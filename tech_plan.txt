架构改造研究与规划报告
一、现有架构深度分析
1.1 当前交互链路
项目目前存在两套并行的调用机制：

机制 A：旧版子进程 RPC（agent.ts，可能是遗留机制）

代码位置：agent.ts
通过 spawn(pi-binary --mode rpc) 启动独立进程
只有基础的 prompt/bash/get_state 等命令
机制 B：原生 SDK 直连（正在使用的主机制） ← 重点分析对象

代码位置：native-ipc.ts、pi-sdk-driver.ts、session-supervisor.ts
1.2 机制 B 具体调用关系（深度集成）
层级	核心文件	关键职责	直接依赖的 pi 类
UI 层	preload/index.ts	暴露 18+ 个 nativeXxx API 到渲染进程	无（仅 IPC 通道名）
IPC 分发	native-ipc.ts	18 个 IPC handler 注册与参数转发	无（仅调用 Driver）
统一入口	pi-sdk-driver.ts	PiSdkDriver 类，对外 20+ 方法 facade	ModelRuntime 类型导入
会话管理	session-supervisor.ts	创建/打开/消息/取消/树导航、工具安全钩子	SessionManager、createAgentSession、AgentSession、DefaultResourceLoader、parseSkillBlock
运行时初始化	runtime-deps.ts	Auth/Models/Settings 初始化、配置同步写文件	ModelRuntime、SettingsManager
类型定义	types.ts	SessionRef / Transcript / ToolCallInfo 等 UI 数据结构	AgentSession、SessionManager、ResourceLoader、ModelRuntime、SettingsManager
1.3 现有机制的强耦合点（改造痛点）
直接内存调用：createAgentSession({ modelRuntime, settingsManager, ... }) 把 pi 的运行时对象直接注入会话，无协议边界
自定义工具注入：customTools: createOfficeTools(workspacePath)（session-supervisor.ts#L119）
同步读取会话状态：sessionManager.getEntries()、sessionManager.getTree() 直接同步遍历内存中的会话树
工具安全拦截：通过 monkey-patch agent.beforeToolCall（session-supervisor.ts#L405-L420）检查路径
会话双写机制：每次 entry_appended 后 fs.copyFileSync(ref.sessionFile, userCopyPath)（session-supervisor.ts#L465-L474）
模型直接操作：active.agentSession.setModel(model)（session-supervisor.ts#L318）
AI 自动命名：调用 modelRuntime.completeSimple(model, context)（session-supervisor.ts#L617-L622）独立发起 LLM 请求生成会话名
二、pi-acp 架构分析
2.1 进程与协议栈（三层隔离）
2.2 关键代码位置
模块	文件	作用
入口	index.ts	stdio 包装 + AgentSideConnection 启动
ACP Agent 实现	agent.ts	initialize/newSession/prompt/cancel/listSessions/loadSession/deleteSession + 配置
ACP 会话管理	session.ts	SessionManager / PiAcpSession：事件翻译、工具状态机、Diff 快照
Pi RPC 包装	process.ts	PiRpcProcess.spawn() → spawn pi CLI，封装所有 RPC 命令方法
翻译层	src/acp/translate/*	prompt / pi-messages / pi-tools / bash 四种消息格式互转
其他	pi-sessions.ts, session-store.ts	扫描/查找 pi 历史会话、id→sessionFile 映射持久化
2.3 pi-acp 的能力边界（与 pi-gui 文档分析一致）
已覆盖的：

✅ Session 生命周期（new/load/list/delete/cancel）
✅ Prompt 流式输出（agent_message_chunk）
✅ Tool Call 展示（tool_call + tool_call_update + locations + structured diff）
✅ 模型/Thinking 配置（setSessionConfigOption / setSessionMode）
✅ 内置 slash commands（compact/export/session/name/steering/changelog 等）
✅ 历史消息回放（loadSession 时逐条重放）
缺失的（Desktop Host 负责）：

❌ Session Snapshot / 完整状态快照（只有增量事件）
❌ 可查询/编辑的消息队列（只暴露 queueDepth 数字）
❌ 工具安全边界（工具由 pi 子进程直接本地执行，无 beforeToolCall 拦截点）
❌ 自定义工具注入（ACP 有 MCP 机制，但 pi-acp 未实现 passthrough）
❌ Extension UI Host（confirm/input/editor/widget/status）
❌ Session Tree 完整导航（ACP 标准里无此概念）
三、两种架构对比
维度	当前 pi SDK 直连	pi-acp 协议
通信边界	同内存函数调用	两层跨进程（ACP→PiRpc→pi）
耦合度	极高（10+ pi 核心类直接 import）	极低（仅依赖 ACP 标准协议 + pi 二进制）
工具执行	在 Electron 主进程内，可通过 beforeToolCall 拦截	在 pi 子进程内，默认无拦截点
状态读取	同步 getEntries/getTree	增量事件累计 / getMessages 回放
自定义工具	customTools 参数直接注入 TS 对象	需要走 ACP MCP 或在 Host 侧代理
可替换性	绑定死 pi	任何 ACP Agent 都可接入（未来可切 Claude Code、opencode 等）
调试复杂度	单进程 TS debugger	三进程 stdio 抓包（ACP JSON + pi NDJSON）
API Key 管理	直接写 auth.json + models.json（runtime-deps.ts#L75-L117）	依赖 pi 已配置 或 --terminal-login
四、改造方案推荐
4.1 核心思路：保留 Host 层产品能力，把底层驱动替换为 ACP
不是让 Electron 变成一个"ACP Client 通过 stdio 连外部 pi-acp 进程"，而是：

在 Electron Main 进程内直接 import pi-acp 的代码作为库使用（去掉 stdio 包装层，直接调用内存对象），同时保留上半层（Session Supervisor / Session Snapshot / 双写备份 / SQLite 索引）。

4.2 为什么不直接"Electron spawn pi-acp 子进程"
因素	子进程方案	内存嵌入方案（推荐）
性能	三层 I/O（Renderer↔Main↔pi-acp↔pi）	两层（Main 内只加 1 层内存调用 + 最终 pi RPC）
自定义工具	需通过 ACP MCP SSE/HTTP（pi-acp 未实现）	可以在 Bridge 层直接拦截 tool_call，Host 执行后伪造 tool_result 写回
会话状态同步	Snapshot/队列需跨进程同步	同内存共享
调试复杂度	三进程	两进程（Electron + pi 子进程）
回滚难度	高	低（同一个 PiSdkDriver 里做 if/else 分支）
五、详细改造步骤规划（分 7 个阶段，可回滚）
阶段 0：前置准备 — 引入 pi-acp 到 third_party（无破坏性）
目标： 确保 third_party/pi-acp 能构建、tsconfig 路径可解析

步骤 0.1：拷贝 ref_open_source/pi-acp → third_party/pi-acp（或添加 git submodule 指向 svkozak/pi-acp）
步骤 0.2：在根 package.json 添加 workspace / path alias 指向 third_party/pi-acp/src
步骤 0.3：安装 @agentclientprotocol/sdk 依赖（目前项目无此依赖）
步骤 0.4：验证 tsc --noEmit 能识别 pi-acp 代码的类型
验收：import { PiAcpAgent } from 'pi-acp' 不报类型错
阶段 1：构建 AcpDriverBridge（最小闭环：init + newSession + prompt）
目标： 跑通"新建会话 → 发 'Hello' → 收到 assistant 文本增量"

步骤 1.1：新增文件 src/main/pi-sdk-driver/acp-driver-bridge.ts
内部构造一个模拟的 AgentSideConnection（不经过 stdio，直接把 ACP SDK 的 notification/sendNotification 回调到 Host）
实例化 PiAcpAgent
暴露方法：initialize() / createSession(cwd) / prompt(sessionId, text) / cancel(sessionId)
暴露事件订阅：onSessionUpdate(sessionId, callback)
步骤 1.2：在 PiSdkDriver 内增加一个 driverMode: 'sdk' | 'acp' 开关（读 config）
步骤 1.3：PiSdkDriver.createSession() 内，当 mode==='acp' 时走 bridge 而不是 SessionSupervisor.createSession
步骤 1.4：把 ACP 返回的 agent_message_chunk 以兼容现有格式通过 eventHandler 广播
验收：启动 App（配置走 ACP 模式）→ 新建会话 → 输入消息 → Timeline 显示 AI 回复文本
阶段 2：补齐 Session 列表 + 历史加载 + Transcript
目标： 历史会话可见、点开会话可看到历史消息

步骤 2.1：Bridge 实现 listSessions(cwd) → 调用 pi-acp 的 listSessions + 扫描本地 ~/.pi/agent/sessions
步骤 2.2：Bridge 实现 loadSession(sessionId) → 调用 pi-acp 的 loadSession，在加载期间收集回放的 user/agent/tool 消息并缓存
步骤 2.3：Bridge 内部维护 transcriptCache: Map<sessionId, SessionTranscriptItem[]>，每次 sessionUpdate 增量追加
步骤 2.4：SessionSupervisor.getTranscript() 当 mode==='acp' 时读 Bridge cache
步骤 2.5：Session 文件路径映射：ACP sessionId → pi sessionFile → 填入 SessionRef.sessionFile（保留后续双写能力）
验收：Sidebar 显示历史会话列表 → 点击某个旧会话 → Timeline 显示历史对话
阶段 3：补齐 Tool Call 展示 + 安全拦截 + 自定义 Office 工具
目标： 工具调用正确显示，且文件工具不出工作区，Office 工具可用

步骤 3.1：Bridge 把 ACP tool_call / tool_call_update 事件翻译成现有 ToolCallInfo 格式，写入 transcriptCache 并广播事件
步骤 3.2：Diff 适配：ACP 已经有结构化 diff，桥接到 UI 现有的 Diff 显示逻辑
步骤 3.3：路径安全（关键） — 两种方案选一个：
方案 A（更优但改动大）：在 PiAcpSession 或其上层拦截所有含 path 的 tool_call，先做 workspace 包含校验，不通过则 reject 并发送 error tool_result
方案 B（兜底）：在 pi 子进程之后、写回 ACP 之前，发现路径违规则发送 abort + UI 告警
步骤 3.4：Office 自定义工具 — 在 Bridge 层增加一个 hostToolRegistry，当 ACP 发 tool_call 命中 office 工具名时，Host 内部执行后注入一个伪造的 tool_result 事件回 pi-acp 的事件流（不需要 pi 子进程真执行）
验收：(1) read/edit/write/bash 工具调用展示正常；(2) 尝试 AI 读取 /etc/passwd 被拦截；(3) 发送"把结果写入 Excel"能执行 Office 工具
阶段 4：运行时管理（模型切换 + Thinking + API Key）
目标： 模型/设置面板可用

步骤 4.1：Bridge 实现 listModels() → 从 PiRpcProcess.getAvailableModels() 返回值提取 provider/modelId
步骤 4.2：Bridge 实现 setModel(sessionId, providerId, modelId) → 调用 ACP unstable_setSessionModel（注意 ACP 传的是 provider/modelId 拼接字符串，在 bridge 里拼）
步骤 4.3：Thinking Level 切换 → 调用 ACP setSessionMode
步骤 4.4：API Key / 模型配置写入 — 继续复用现有 runtime-deps.ts: syncAgentModelConfig() 直接写 auth.json/models.json 文件（因为 pi-acp spawn 的 pi 子进程也会读这些文件），这块保留原逻辑，不需要通过 ACP
步骤 4.5：自动会话命名 — 同样保留原逻辑（不经过 ACP，直接用 modelRuntime），因为这是 Host 产品功能
验收：设置页切换模型 → 下一条消息使用新模型；切换 thinking level 生效；新配置的 API Key 重启后生效
阶段 5：Session Tree / 队列 / 运行状态 等高级产品特性
目标： 恢复 SDK 模式下的产品体验

步骤 5.1：Session Tree — ACP 标准没暴露，但 PiRpcProcess 可以调 getMessages，用 parentId 在 Host 侧构造成树结构（Bridge 自己维护）。navigateTree 则调用 pi-acp 的 compact 或通过 prompt 注入 "从节点 X 继续"
步骤 5.2：可编辑队列 — Bridge 层自己维护 queuedMessages[]，不依赖 ACP 的内部 turnQueue。上一条 AI settled 后从队列取：
steer 模式 → 通过 pi-acp 的 /steering slash command 注入
followUp 模式 → 普通 prompt
步骤 5.3：取消 — ACP cancel() 已经完整支持
步骤 5.4：Status + 队列深度广播 — 从 ACP session_info_update._meta.piAcp.{running, queueDepth} 提取，翻译成现有事件格式
验收：AI 运行时能追加 follow-up 消息并排队执行；取消按钮立即终止；会话树能正确显示父子关系（或降级显示线性列表但不丢失消息）
阶段 6：技能（Skills）+ Slash Commands + 会话双写/索引
目标： Skills 与现有 app-config 机制兼容，会话可恢复

步骤 6.1：Bridge 监听 ACP available_commands_update，把命令列表映射为现有 SkillInfo[]（/skill:xxx 前缀匹配）
步骤 6.2：invokeSkill() 发送对应的 slash command 通过 prompt 流
步骤 6.3：会话双写 — 复用原 syncSessionCopy 逻辑，但触发时机从"监听 pi SDK entry_appended"改为"监听 ACP 增量事件累积一条就触发"
步骤 6.4：SQLite 索引 — 同样在 session_info_update 时 upsertIndex
步骤 6.5：session rename — ACP /name slash command
步骤 6.6：session compaction — ACP /compact slash command
验收：Skill 列表显示；调用 Skill 生效；重启后 userData 中的会话副本和 SQLite 索引完整
阶段 7：清理 + 开关 + 回滚保障 + 测试
目标： 生产可上线，随时可切回 SDK 模式

步骤 7.1：在 resources/config/app-config.json 增加 agent.driverMode: "sdk" | "acp" 配置项，默认 "sdk"（先灰度）
步骤 7.2：把 PiSdkDriver 内所有 if/else 分支加上明确注释（// TODO: 当 ACP 稳定后，删除 SDK 分支），不要急着删老代码
步骤 7.3：验证回滚：切回 driverMode=sdk 后老功能 100% 可用
步骤 7.4：编写契约测试（独立 test 文件）：

步骤 7.5：在 GetDiagnostics 上跑 typecheck + npm run build 确保通过
验收：切换配置开关可无缝切换两种驱动；构建无错；核心场景测试通过
六、风险与注意事项
风险	影响	缓解措施
pi-acp 的 @agentclientprotocol/sdk 版本与现有 TS 配置冲突	编译失败	先在独立 tsconfig 验证 ACP 编译再合入主工程
Office 自定义工具的 tool_result 回注时序错乱	AI 看不到工具结果卡住	在 Bridge 内严格等待 pi 子进程 tool_call 到达后再异步注入 tool_result
路径安全拦截失败（工具在 pi 子进程执行完了才拦截）	数据安全风险	优先选择方案 A（在 PiAcpSession.tool_call 触发前拦），不选 post-hoc
pi-acp 升级后内部 API 变化	Bridge 失效	pin 住 third_party/pi-acp 的 commit hash，不要盲目跟随 upstream
loadSession 时 ACP 回放事件与增量事件交错	Transcript 重复/乱序	在 Bridge 内维护 isReplaying flag，回放完成后才接收实时增量
MCP 未来需要接入	ACP mcpServers 参数被忽略	pi-acp 目前不做 passthrough，可在阶段 7 之后再开一条 MCP Client 通道给 Host 用
